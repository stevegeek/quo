# Quo 2.x design notes

> Status: spike. Subject to change. Not a public commitment.

## The core cut

Quo 1.x has two composition modes that look identical (`+`) but cost
very different things:

- **Class composition** (`SomeClass + OtherClass`) — defines a new
  named query type. Returns a Class. Heavy: allocates a Ruby class,
  re-registers Literal properties, defines class-level metadata.
- **Instance composition** (`some_instance + other_instance`) — combines
  query values at a call site. Should be cheap.

In 1.x, the instance path **internally goes through the class path**:
`merge_instances` dispatches to a strategy that calls `Composing.composer`,
which calls `Class.new` and `prop` for every `q1 + q2` invocation. The
fresh class is then immediately instantiated once and thrown away. That's
the source of most of the per-request composition cost we measured.

Quo 2.x makes the two modes **physically different**:

| Mode | Returns | Implementation |
|---|---|---|
| Class composition (`Q1 + Q2`) | `Class` | `Class.new(super)` + Literal `prop` (unchanged from 1.x) |
| Instance composition (`q1 + q2`) | Value-shaped query | Two single concrete classes (`Quo::ComposedRelationBackedQuery`, `Quo::ComposedCollectionBackedQuery`) with `(_left, _right, _joins)` as instance state. Zero class allocation. |

## What instance composition looks like in 2.x

```ruby
# This:
q = (CommentsByAuthorQuery.new(author_id: 1) +
     UnreadCommentsQuery.new)
q.results

# In 1.x, allocates: 1 anonymous Class, ~70 Literal::Property entries,
#   ~140 schema entries, plus the merged-prop hash and the strategy +
#   registry instances.
#
# In 2.x, allocates: 1 Quo::ComposedRelationBackedQuery instance (a
#   Literal::Struct with three ivars: _left, _right, _joins).
```

The composed instance walks the operand tree at materialisation time,
calling each operand's existing `unwrap_unpaginated` (for relations) or
delegating directly (for collections). Each operand carries its own
props, specs, and transformer — there's nothing for the composer to
extract or re-apply.

## What stays the same

- **Public API.** `q1 + q2` still returns something that responds to the
  full `Quo::Query` instance API: `#results`, `#unwrap`, `#to_sql`,
  `#paged?`, `#transform?`, `#count`, etc. Tests written against this
  surface should continue to pass.
- **Class composition.** `Q1 + Q2` between classes still returns a Class.
  Existing constants like `RecentNonSpamComments = Q1 + Q2` keep working.
- **The leaf query class API.** `prop`, `query`, `collection`, `transform`,
  `wrap`, etc. — unchanged.
- **Specifications.** Each leaf instance still owns its own
  `_specification`. Composition just refers to the leaf — no merge,
  no copy, no extraction.
- **Pagination, transformers.** Per-instance state on the composed value.

## What changes (and why)

### `Quo::Composing.merge_instances` no longer calls `Composing.composer`

The instance path stops going through the class path. Direct construction
of the new concrete composed classes, no strategy chain, no registry.

The four `*Strategy` classes under `composing/` for instance composition
(`QueryAndQueryStrategy`, `QueryAndRelationStrategy`,
`RelationAndQueryStrategy`, `RelationAndRelationStrategy`) become
unused on the instance path. They're retained for now because:

1. The class path still uses `QueryClassesStrategy`.
2. We may keep them for users who explicitly call into `Composing` for
   their own reasons.

A follow-up could remove the unused instance strategies entirely. Not in
this spike.

### Two new concrete classes

```ruby
class Quo::ComposedRelationBackedQuery < Quo::RelationBackedQuery
  prop :_left,  _Any
  prop :_right, _Any
  prop :_joins, _Nilable(_Any)

  def query
    # walks the tree using existing merge_left_and_right semantics,
    # operating on instance state (@_left / @_right) rather than
    # class-level @_left_query / @_right_query
  end
end

class Quo::ComposedCollectionBackedQuery < Quo::CollectionBackedQuery
  # same shape, returns Enumerable from #collection
end
```

The merge logic itself is unchanged — same Relation+Relation,
Relation+Collection, Collection+Collection cases as 1.x's
`merge_left_and_right`. Only the operand source differs (instance ivars
vs class ivars).

## `copy` on a composed instance

`Quo::Query#copy(**overrides)` is preserved on composed instances with the
same external semantics as on a leaf: "return a new instance, override
some of the props that were used to construct it." The internal mechanism
differs:

- Overrides matching the composed's own props (`_left`, `_right`,
  `_joins`, `_specification`, `page`, `page_size`) go through the
  standard Literal `Quo::Query#copy`.
- Overrides for any other key are treated as **fan overrides**: walk
  the operand tree, recursing into composed operands, and apply the
  override to *every* `Quo::Query` operand (at any depth) that declares
  the prop. Conceptually the composed query exposes one logical prop —
  copying with a new value lands on every leaf that owns it.
- Unknown prop (no operand declares it) → `ArgumentError`. Same surface
  as a normal `copy(unknown_prop:)`.
- Right-precedence in 1.x was about *value selection* when both
  operands were constructed with the same prop name (`Q1(score: 0.5) +
  Q2(score: 0.7)` resolved to 0.7 across the merged class). In v2,
  each leaf keeps its own constructor-time value, so the merged
  relation is the AND of both. `copy` doesn't have that ambiguity to
  resolve: it sets the new value on every leaf that names the prop.

Cost: `copy(fan_prop: x)` is `O(tree size)` because each fan override
walks the operand tree once. This is deliberately not on a hot path —
documented as such for users who care.

## Value-form constructors: `Quo::RelationBackedQuery.from(rel)` / `Quo::CollectionBackedQuery.from(enum)`

In 1.x, the recommended way to wrap an arbitrary AR scope as a Quo::Query
was `Quo::RelationBackedQuery.wrap(rel).new`. The `wrap` half allocates an
anonymous class; `.new` then instantiates it once and the class is
discarded. On hot paths (e.g. an aggregate that builds a query per
request), this is the same shape of waste as 1.x's instance composition.

2.x adds value-form constructors that return an instance directly, with
no class allocation:

```ruby
# 1.x and still valid in 2.x (for type-defining use):
Foo = Quo::RelationBackedQuery.wrap(Comment.where(read: false))  # returns Class
Foo.new.results

# 2.x value form (preferred at call sites):
Quo::RelationBackedQuery.from(Comment.where(read: false)).results
Quo::CollectionBackedQuery.from(some_array).results
```

Implementation: two new concrete classes,
`Quo::WrappedRelationBackedQuery` and `Quo::WrappedCollectionBackedQuery`.
Each declares a single `:_wrapped` prop and overrides `#query` /
`#collection` to return it. `.from` is the constructor.

Both interoperate seamlessly with v2 instance composition — they're
`Quo::Query` instances, so `q.from(rel) + other_q` produces a
`Quo::ComposedRelationBackedQuery` like any other.

`.wrap` is kept unchanged for two reasons:

1. The class-returning form is the right shape for *type-defining* use
   (constant assignment) and is widely used in the existing test suite.
2. The block form (`wrap(props: {x: T}) { ... }`) can't be expressed as
   a value — the block needs a class to be a method definition.

## What we explicitly are NOT doing in this spike

- Not removing the class composition path. `Q1 + Q2` between classes
  keeps its current cost. That cost is fine because it runs once at
  load time when used correctly.
- Not removing prop fan-out from the class path. Users who rely on
  `(Q1 + Q2).new(some_q1_prop:, some_q2_prop:)` keep that behaviour.
  The skill already steers users away from this pattern at call sites.
- Not changing the `Quo::Query` base class.
- Not breaking the existing test suite. Every existing test should
  still pass against the spike. If something fails, it's a bug we
  introduced.

## Initial benchmark — main (1.0.0) vs 2.x-spike

Workload: 5000 iterations of `(L.new + R.new + T.new).unwrap.to_sql`,
where L/R/T are three small `RelationBackedQuery` subclasses with one
prop each. Identical leaf classes on both branches.

| metric                | main (1.0.0)        | 2.x-spike           | Δ              |
|-----------------------|---------------------|---------------------|----------------|
| wall                  | 3805 ms (761 µs/op) | 1740 ms (348 µs/op) | 2.2× faster    |
| GC time               | 238 ms (65 collections) | 61 ms (40 collections) | 4× less |
| allocations           | 8,000,091 (1600/op) | 4,755,036 (951/op)  | -41%           |
| T_CLASS allocations   | 753                 | **0**               | -100%          |

The T_CLASS line is the crux: instance composition in 2.x allocates
zero new Ruby classes per call. This is structural — the path no longer
goes through `Composing.composer`, so `Class.new` simply isn't called.

Note this is *on top of* the perf fixes already shipped in 1.0.0 (beta3).
v2 takes another ~2× cut beyond that.

## Open questions for later phases

- **Pagination on a composed instance.** Today the composed class
  inherits `:page` and `:page_size` from `Quo::Query`. The instance form
  works the same. But: do we want to refuse pagination on a composed
  instance whose operands are themselves paginated? Current behaviour:
  composed wins. Probably fine.
- **Transformer precedence.** When both operands have transformers,
  whose wins? Today the merged class accepts a single transformer; we
  follow the same rule on the composed instance.
- **Removing the unused instance strategies.** Cosmetic / dead code.
  Worth a follow-up commit, not part of this spike.
- **Class composition cleanup.** Once the perf-sensitive path no longer
  uses `composer`, we could revisit whether `composer` itself can be
  simplified. Not critical for 2.x.
- **Migration guide.** What does a 1.x user notice when they bump? The
  goal is "nothing, except their app gets faster." That's the bar.
